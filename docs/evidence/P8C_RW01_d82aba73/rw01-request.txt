## 1. Problema normativo

Dos pares independientes de bases P5a/P5b pueden contener originales válidos con el mismo `(watch_id, revision)` y entradas Watchlist diferentes.

Ambos pueden generar señales originales válidas e identidades `walt1_` diferentes.

Actualmente, el writer permite que ambas se inserten en el mismo outbox. Después, `_verify()` detecta la contradicción entre entradas y rechaza el almacenamiento.

**Invariante obligatorio:**

Toda escritura `recorded` debe preservar las propiedades semánticas exigidas por el verificador completo.

En particular, para cualquier clave `(watch_id, revision)` almacenada, todas sus evidencias deben mantener la misma entrada Watchlist canónica completa.

## 2. Reproducción obligatoria

Antes de corregir:

1. Verificar HEAD/tree y estado de trabajo.
2. Reproducir el escenario público descrito por el Orchestrator utilizando Python 3.13 soportado.
3. Utilizar dos pares originales genuinos, con el mismo watch_id/revision y diferentes `target_price_minor`.
4. Ejecutar exclusivamente las APIs públicas para crear las fuentes y admitir las señales.
5. Confirmar el defecto original: dos `recorded`, seguidos de fallo de `verify` y `backup`.
6. Preservar código del probe, salida, versión Python/SQLite y SHA/tree del candidato defectuoso.

No emplear DTO falsificados, mutaciones SQL, acceso directo al writer ni modificaciones de fuentes para fabricar el caso.

No sobrescribir el resultado pre-fix después de corregirlo.

## 3. Corrección autorizada

Owner principal: **DB-OWNER**.

ARQ/BE debe revisar la semántica de conflicto e identidad. SEC/SRE revisará la atomicidad y los failure modes.

Implementar una validación transaccional que:

- Se ejecute dentro del mismo `BEGIN IMMEDIATE` de `_enqueue_verified()`.
- Compare la nueva entrada Watchlist contra todas las entradas existentes que compartan `(watch_id, revision)`.
- Utilice la representación completa, normalizada y canónica de la entrada.
- Rechace una incompatibilidad antes del COMMIT, sin modificar el outbox previamente sano.
- Mantenga una categoría pública de conflicto documentada y estable. Para una misma identidad histórica con contenido incompatible, evaluar `identity_conflict` (exit 2), manteniendo `replay_conflict` para los conflictos ya definidos de un mismo alert ID.
- Distinga corrupción preexistente (`storage_corrupt`) de un nuevo intento incompatible.
- Respete un único Budget compartido, default 2 y máximo 5 segundos.

La validación debe usar lecturas acotadas y verificadas. No aceptar JSON almacenado como autoridad sin reconstrucción semántica.

**Prohibido:**
- Eliminar o debilitar el invariante del verificador.
- Modificar identidades `walt1_`, `wsig1_` o anteriores.
- Cambiar esquemas SQLite ya congelados.
- Aumentar deadlines.
- Introducir retries que oculten conflictos.
- Modificar fuentes P5a/P5b.
- Ampliar el alcance de la fase.

Si alguna de estas restricciones resultara incompatible con una corrección correcta, detener el trabajo afectado y elevar la decisión al Phase Lead.

## 4. Regresiones obligatorias

Desarrollar pruebas automatizadas para:

1. Mismo watch_id/revision, distinta entrada y diferente signal_id.
2. El mismo caso con destination_key diferente.
3. El mismo caso con series diferentes.
4. Dos procesos concurrentes intentando introducir configuraciones incompatibles.
5. Dos copias independientes de fuentes con la misma configuración semántica: deben coexistir cuando sus señales/destinos sean distintos.
6. Revisiones diferentes: no provocar conflictos artificiales.
7. Productos y watch_id distintos: independencia preservada.
8. Replay antiguo válido: comportamiento original inalterado.
9. Tras rechazo: bytes, cardinalidad, evidencia y first_prepared_at originales inalterados.
10. Tras rechazo: `verify` y `backup` continúan funcionando.
11. Bases P5a/P5b originales: bytes inalterados.
12. Timeout o error entre comprobación y escritura: rollback sin estado parcialmente confirmado.

Incluir una prueba con fuentes legítimas, no solo mocks ni fixtures construidas mediante helpers de producción.

El test debe fallar contra el candidato defectuoso y pasar contra la corrección.
